# Smartcloud verification registry

This is the canonical Markdown registry for the shipped GitHub Action, its runtime features and every workflow in this repository. It records how to reach behavior and what proves it works. The runtime registry remains `FEATURES` in `packages/runtime/src/features.ts`; this document does not configure runtime behavior.

## Run the funnel

1. Run `node --run setup` on Node 24 or later. It installs dependencies, builds the workspace and installs the pre-commit hook outside CI. An existing hook is preserved; setup fails with instructions rather than overwriting it.
2. Immediately after coding, run `node --run funnel:static` before documentation or other work. This runs Nx lint/typecheck and type-checks every test project. Fix the reported code rather than weakening a rule.
3. Run `node --run funnel:verify` for all contract suites and coverage. For one feature, use the command in the table below. `node --run funnel:contracts` checks registry completeness and exercises corrective lint diagnostics and the hook against disposable Git repositories.
4. Update this registry when a feature or workflow changes, then run `node --run check`. The runtime test cache includes this file and the workflow files. PR CI runs funnel contracts in its always-on lint job, including documentation-only changes; its existing test, typecheck and smoke jobs remain required by `check`.
5. Record the command, commit/tree, exit status and decisive output. Label GitHub-only checks as pending until a run URL proves them. A dry run is not proof that a write permission works.

The pre-commit hook runs `verify:static` (the existing `funnel:static` gate), then `test:affected` for the staged tree. It does not run the full verification pipeline, smoke jobs or evidence publication. CI and `node --run check` retain full verification. The hook refuses unstaged tracked changes and non-ignored untracked files, because tests read the worktree rather than the index. Stage the intended change or use a clean task worktree. It never stashes or rewrites someone else's work. The existing house commit-msg hook still checks attribution and commit policy. No extra dependencies or runtime flags are required.

To check staged behavior manually, stage the intended files with `git add <paths>`, then run `node --run test:affected`. It uses Nx's dependency graph to run the affected test projects and their normal coverage gates, without prerequisite build targets: tests resolve workspace TypeScript sources directly. Files outside Nx projects, including workflow/registry/toolchain files, conservatively select every test project. Paths containing spaces or commas also select every test project rather than being split incorrectly by Nx's file-list interface. Empty staged changes run no tests; Git, graph or test failures return a nonzero exit. A project change with no test owner fails with instructions to add one.

By default, the adapter reads the current Git index. The native hook passes `--staged-tree <tree>` to retain its captured index after clearing Git-local variables from verification children. This internal option accepts a Git tree, not a branch or commit. Run `node tools/test/file.ts tests/tools/src/affected.spec.ts` to prove staged-only/transitive selection, captured and alternate indexes, workspace-wide selection, failure propagation and rejection of build execution using disposable real Nx workspaces.

The hook records the initial staged tree and checks it, tracked worktree changes and untracked files after each phase. A generator that changes files or stages its output invalidates the run even when it exits successfully. Review its output, stage the intended changes and rerun verification; the hook leaves those changes intact. Verification children do not inherit Git-local variables such as `GIT_INDEX_FILE`, so nested repositories use their own Git state. The hook's own inspections retain those variables to check the index Git will actually commit, including temporary or alternate indexes.

Run `node --run funnel:contracts` to exercise real installed-hook commits: staged, unstaged and untracked mutation in either phase must reject the commit; unchanged input, foreign-hook preservation and isolated child Git operations remain controls. These phase-boundary checks detect persistent drift, not a hostile process that changes and restores files between observations. Avoid concurrent source or index writers during a commit.

Installation creates the hook exclusively, so a concurrent writer cannot have its hook overwritten. Reinstalling an identical hook leaves its contents and modification time unchanged; an unreadable or different existing hook stops installation with a preservation diagnostic.

Shared setup composes the existing native hook through `.agents/surfaces.jsonc` with `preCommit: { "script": "funnel:pre-commit", "marker": "smartcloud-funnel pre-commit" }`. It requires that script plus `verify:static` and `test:affected`; it does not install a second verification runner. The hook fixtures run this installer twice, preserve foreign hooks, reject unsafe or missing script declarations, and reject a real commit when affected tests fail.

To improve the funnel after a repeated mistake: fix the example people copy, add a lint diagnostic saying what to do instead or a regression test showing the contract, prove that the old case fails and the corrected case passes, then remove the duplicate prose. Keep approvals, ownership, sensitive-data decisions and unresolved tradeoffs in agent guidance.

## Action entry point

`action.yml` ships one Node action, built as `dist/index.js`. CI's `smoke` matrix calls `uses: ./` for `pull_request`, `issues`, `push` and `schedule` with `tools/ci/smoke/config.yml`, `dryRun: true` and `telemetry: false`. `tools/ci/smoke/replay.ts` substitutes the checked-in event payloads. `tools/ci/smoke/check.ts` checks the feature-result table, expected change lines and dry-run heading against `expected.json`. The smoke summaries are the evidence, not an invented UI screenshot.

Local deterministic entry-point proof: `pnpm nx test @resnovas/action-tests`. Tests invoke the action program with injected GitHub services and verify input parsing, restricted tokens, reports and exit behavior. `pnpm bundle:check` verifies the bundle can be produced within its budget. Neither is a live GitHub workflow run. The workflow smoke requires GitHub read access and is exercised by PR CI, not by dispatching a production workflow manually.

Feature event kinds below are the engine's decoded envelopes: `pullRequest` comes from PR-related events, `issue` from issue events, `comment` from issue comments, and `repository` from repository-wide events. The exact workflow subscriptions are in the workflow table. A feature being registered does not mean this repository subscribes to every event it could consume. Repository sweeps generally run on push, schedule or workflow_dispatch. Backports require a closed, merged PR; commands require an authorized commenter. `required` additionally needs the action's check-run ID and is intentionally skipped by ordinary CLI dry runs.

## Evidence

Attach output to the owning issue/PR when identifiers exist. Record missing mappings explicitly; never reuse an unrelated issue. Evidence must name the revision, command and observation, for example: the corrective lint fails on the old source and passes after the fallback is expressed explicitly. A future feature needs a rejecting control as well as a successful path.

The registry contract checks exact feature names/handles, test-suite paths, workflow file coverage and top-level event names. It does not prove prose completeness, all event subtypes, token grants or live effects. The workflow observations above name those remaining checks. New reusable workflow behavior needs evidence from its owning house repository.

Known migration boundaries: the MCP stdio entry point retains its top-level await with one explained lint exception; its startup rejection and lifetime need a dedicated lifecycle migration. Synchronous pattern/config parsers retain existing throw contracts. Integration SDK callbacks remain outside the production syntax restrictions. These are not claims of complete Effect-boundary enforcement.

If registry checks fail, update the relevant row with the real registration/trigger and a test that checks observable behavior. If a fixture lint test fails, fix the selector or its code example, keeping its positive and negative controls. If the hook reports a different staged tree, preserve the unstaged work and use an isolated checkout rather than bypassing checks.

## Required checks on merge-group commits

Tracking: [SMC-176](https://linear.app/resnovas/issue/SMC-176) and [issue #749](https://github.com/Resnovas/smartcloud/issues/749). This runtime correction extends the registry from merged PR #750.

| Feature    | Trigger                                                | Prerequisites                                                                                   | Verification                                    | Expected evidence                                                                                                                     |
| ---------- | ------------------------------------------------------ | ----------------------------------------------------------------------------------------------- | ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `required` | Pull request events or `merge_group: checks_requested` | `required` configured, `smartcloud-required` enabled (default true), current job's `checkRunId` | `pnpm nx test @resnovas/feature.required-tests` | The decoded merge-group head SHA determines passed, failed, pending and missing-check findings. Original PR checks cannot substitute. |

### Reproduce locally

Install the locked workspace dependencies with `pnpm install --frozen-lockfile`, then run:

```sh
node tools/test/file.ts tests/feature.required/src/feature.spec.ts
pnpm nx run-many -t test typecheck docgen contracts -p @resnovas/engine @resnovas/engine-tests @resnovas/feature.required @resnovas/feature.required-tests
```

The feature tests pass a `checks_requested` payload through `runFeatures` and the real `decodeEvent`, then provide checks keyed by SHA through the in-memory GitHub service. Opposite outcomes on the original PR SHA catch querying the wrong commit. The test clock advances to exercise the existing timeout without waiting a real minute.

Expect `required.passed` only for successful queue checks; expect error findings `required.failed`, `required.pending` or `required.missing` for the corresponding cases. The aggregate excludes its own in-progress job. Missing `checkRunId` fails closed in action mode. Pushes, schedules, dispatches and destroyed merge groups neither poll nor require a check-run ID. Existing PR polling and exclusion tests remain controls.

Before the correction, the focused suite reports `5 failed | 20 passed`: all four merge-group outcomes are skipped and the missing-job-ID case has no error finding. After the correction it reports `25 passed`. This is deterministic runtime evidence, not a live queue run.
