---
title: 'Conditions'
description: 'The condition language used by labelling, conventions, reviews and stale exemptions.'
---

A condition group is a list of conditions and the number of them that must pass. It appears wherever a rule has a `when`: labelling rules, convention rules, requested and automatic approvals, and `stale.exempt.when`.

```yaml
when:
  requires: 1
  condition:
    - type: titleMatches
      condition: '/^fix/i'
    - type: branchMatches
      condition: '^hotfix/'
```

`requires` defaults to the number of conditions, so without it every condition must pass. With `requires: 1` any one is enough.

Field names are the same as v1 (`type`, `condition`, `requires`, `label`, `min`, `max`), so v1 conditions work unchanged.

## Patterns

Conditions that match text take a pattern: a regular expression written either bare (`^feat`) or delimited with flags (`/^feat/i`). An invalid pattern is rejected when the config is loaded, not on the first event.

`filesMatch` is the exception: it takes a glob such as `docs/**` or `**/*.md`.

## Conditions

| Type                  | Fields                                                              | Passes when                                                                                                                                            |
| --------------------- | ------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `titleMatches`        | `condition`: pattern                                                | The title matches.                                                                                                                                     |
| `descriptionMatches`  | `condition`: pattern                                                | The description matches. An empty description never matches.                                                                                           |
| `creatorMatches`      | `condition`: pattern                                                | The author's login matches.                                                                                                                            |
| `authorAssociation`   | `condition`: list of associations                                   | The author's association with the repository is one of those listed, or the author is a bot when `bot` is listed.                                      |
| `hasAssignee`         | `condition`: boolean                                                | Someone is assigned (`true`), or nobody is (`false`).                                                                                                  |
| `assigneeMatches`     | `condition`: pattern                                                | An assignee's login matches.                                                                                                                           |
| `reviewerMatches`     | `condition`: pattern                                                | A reviewer of the pull request matches: someone asked to review (a login, or a team's slug), or someone who has reviewed.                              |
| `branchMatches`       | `condition`: pattern                                                | The pull request's head branch matches.                                                                                                                |
| `baseBranchMatches`   | `condition`: pattern                                                | The pull request's base branch, the one it merges into, matches.                                                                                       |
| `isOpen`              | `condition`: boolean                                                | The subject is open (`true`) or closed (`false`).                                                                                                      |
| `isLocked`            | `condition`: boolean                                                | The conversation is locked (`true`) or unlocked (`false`).                                                                                             |
| `isDraft`             | `condition`: boolean                                                | The pull request is a draft (`true`) or ready for review (`false`).                                                                                    |
| `hasLabel`            | `label`: name, `condition`: boolean                                 | The subject has the label (`true`) or lacks it (`false`). Names compare ignoring case.                                                                 |
| `isStale`             | `condition`: days                                                   | There has been no activity for at least this many days.                                                                                                |
| `isAbandoned`         | `condition`: days, `label`: name                                    | The subject carries `label` and has had no activity for at least this many days.                                                                       |
| `filesMatch`          | `condition`: glob                                                   | At least one changed file matches.                                                                                                                     |
| `changesSize`         | `min`, optional `max`: lines                                        | Lines added plus deleted are at least `min` and below `max`.                                                                                           |
| `pendingReview`       | `condition`: boolean                                                | Some requested reviewers have not reviewed yet (`true`), or none are pending (`false`).                                                                |
| `requestedChanges`    | `condition`: boolean                                                | A reviewer's latest review requests changes (`true`), or none does (`false`).                                                                          |
| `isApproved`          | `condition`: count, optional `allowPending`: boolean                | No reviewer is requesting changes, at least this many approved, and no reviewer is pending. With `allowPending: true`, pending reviewers do not block. |
| `commitMessagesMatch` | `condition`: pattern, optional `scope`                              | Commit messages match.                                                                                                                                 |
| `commitsSignedOff`    | `condition`: boolean                                                | Every non-merge commit has a `Signed-off-by` trailer matching its author's email (`true`), or not (`false`).                                           |
| `hasTrailer`          | `trailer`: key, optional `condition`: pattern, optional `scope`     | Commits carry the trailer, with a value matching the pattern when one is given.                                                                        |
| `hasConflict`         | `condition`: boolean                                                | The pull request conflicts with its base branch (`true`), or does not (`false`).                                                                       |
| `checksPass`          | `checks`: list of check names, `condition`: boolean                 | Every named check succeeded (`true`), or at least one has not (`false`).                                                                               |
| `checkStatus`         | `check`: check name, `condition`: `success`, `failure` or `pending` | The named check is in that state.                                                                                                                      |

Activity is GitHub's `updated_at` time for the issue or pull request.

Reviews count each reviewer's latest decisive review: comments and pending reviews do not change an earlier approval or change request.

`isApproved` waits for every requested reviewer by default, as in v1. To pass once enough reviewers have approved, even while others are still requested, set `allowPending`. A change request still blocks.

```yaml
- type: isApproved
  condition: 2
  allowPending: true
```

`baseBranchMatches` matches the branch a pull request targets, so a rule can treat pull requests into a release branch differently from those into `main`. Anchor the pattern to match the whole name: `^main$` does not match `maintenance`.

```yaml
- type: baseBranchMatches
  condition: '^release/'
```

`authorAssociation` reads GitHub's author association, so a rule can treat newcomers, outside collaborators or bots differently from maintainers. It passes when any listed value applies:

| Value                  | The author                                                                     |
| ---------------------- | ------------------------------------------------------------------------------ |
| `owner`                | Owns the repository.                                                           |
| `member`               | Is a member of the organisation that owns the repository.                      |
| `collaborator`         | Was invited to collaborate on the repository: an outside collaborator.         |
| `contributor`          | Has had a contribution merged before.                                          |
| `firstTimeContributor` | Is contributing to the repository for the first time, including a first-timer. |
| `firstTimer`           | Is contributing to GitHub for the first time.                                  |
| `mannequin`            | Is a placeholder for an imported user.                                         |
| `none`                 | Has no association with the repository.                                        |
| `bot`                  | Is a bot account, such as a GitHub App, whatever its association.              |

```yaml
- type: authorAssociation
  condition: [firstTimeContributor, bot]
```

It applies to issues and pull requests, and works in a stale sweep's `exempt.when`. When GitHub reports an association smartcloud does not know, only `bot` can match.

`hasAssignee` and `assigneeMatches` read who is assigned, so a rule can label unowned issues for triage or route work by owner. `assigneeMatches` passes when any assignee's login matches, and never when nobody is assigned. Both apply to issues and pull requests, and work in a stale sweep's `exempt.when`: to keep claimed issues open, exempt anything assigned.

```yaml
exempt:
  when:
    condition:
      - type: hasAssignee
        condition: true
```

`reviewerMatches` passes when any reviewer of a pull request matches: the users and teams asked to review, and everyone who has reviewed. A requested team matches by its slug, such as `security`, without the organisation. GitHub stops listing a requested reviewer once they review, and they then count as someone who has reviewed, so the condition holds before and after their review.

```yaml
- type: reviewerMatches
  condition: '^security$'
```

### Pull request only conditions

`branchMatches`, `baseBranchMatches`, `reviewerMatches`, `isDraft`, `filesMatch`, `changesSize`, `pendingReview`, `requestedChanges`, `isApproved`, `commitMessagesMatch`, `commitsSignedOff`, `hasTrailer`, `hasConflict`, `checksPass` and `checkStatus` only apply to pull requests. On an issue they fail, with the explanation "only applies to pull requests".

### Commit conditions

`commitMessagesMatch`, `commitsSignedOff` and `hasTrailer` ignore merge commits. `scope` is `all` (the default: every commit must match) or `any` (at least one must).

Trailers are read the way git reads them: only from the final paragraph of the message, with keys compared ignoring case. A message with a single paragraph has no trailers, so a subject such as `feat: add x` is never read as a trailer.

```yaml
- type: hasTrailer
  trailer: Signed-off-by
  scope: all
- type: commitMessagesMatch
  condition: "^(feat|fix|docs|chore)(\\(.+\\))?!?: "
  scope: any
```

### Merge conflicts

`hasConflict` reads GitHub's mergeability for the pull request. GitHub works it out in the background, so a freshly updated pull request can briefly be unknown: smartcloud reads it again a few times, two seconds apart, and if it is still unknown, counts the pull request as not conflicting.

```yaml
labelling:
  conflict:
    label: 'Status: Conflict'
    on: [pullRequest]
    when:
      condition:
        - type: hasConflict
          condition: true
```

Like every labelling rule, it is evaluated when the pull request gets one of the events your workflow runs on, such as a push to its branch, an edit, reopening it or a review. A push to the base branch can create a conflict without any pull request event, and `push` and `schedule` runs do not evaluate labelling rules yet, so the label follows on the pull request's next event.

### CI checks

`checksPass` and `checkStatus` read the CI checks on the pull request's head commit: check runs, such as GitHub Actions jobs, and commit statuses, which older CI services post, under their context name. A check is named exactly as GitHub shows it in the pull request's checks list, for example `test (ubuntu-latest)`; names are not patterns and compare with case.

- A check is `success` when it passed, or finished as neutral or skipped. It is `failure` when it finished any other way: failed, cancelled, timed out or needing action. Until it finishes it is `pending`.
- A named check that has not reported yet is `pending`, so `checksPass` does not pass until every named check has run.
- When a name is reported more than once, for example by a workflow that runs on both `push` and `pull_request`, the worst state counts: `failure`, then `pending`, then `success`. A re-run replaces the run it repeats, so a passing re-run clears an earlier failure.

```yaml
labelling:
  ready:
    label: 'Status: Ready to merge'
    on: [pullRequest]
    when:
      condition:
        - type: checksPass
          checks: [build, test]
          condition: true
        - type: isApproved
          condition: 1
  failing:
    label: 'Status: CI failing'
    on: [pullRequest]
    when:
      condition:
        - type: checkStatus
          check: test
          condition: failure
```

Do not name smartcloud's own check runs: they are still running while smartcloud evaluates the rule, so they are always `pending`.

Reading commit statuses needs the `statuses: read` permission in your workflow, as well as `checks`; without it, the rules that use these conditions fail with a permissions error. A check that finishes does not start a smartcloud run by itself, so, as with `hasConflict`, the result follows on the pull request's next event.

Conditions that need a pull request's files, reviews, commits, mergeability or checks cost an API call each. smartcloud loads only the ones the configured rules use.

## Combinators

Combinators nest condition groups.

| Type    | Fields                                         | Passes when                            |
| ------- | ---------------------------------------------- | -------------------------------------- |
| `$and`  | `condition`: list of groups                    | Every group passes.                    |
| `$or`   | `condition`: list of groups                    | At least one group passes.             |
| `$only` | `requires`: count, `condition`: list of groups | Exactly `requires` of the groups pass. |
| `$not`  | `condition`: a group                           | The group fails.                       |

```yaml
when:
  condition:
    - type: $or
      condition:
        - condition:
            - type: filesMatch
              condition: 'docs/**'
        - condition:
            - type: titleMatches
              condition: '^docs'
    - type: $not
      condition:
        condition:
          - type: creatorMatches
            condition: '^dependabot'
```

`$not` also accepts the two forms v1 wrote: a one-item list holding the group, or the conditions inline with `requires` on the `$not` itself.

```yaml
- type: $not
  requires: 1
  condition:
    - type: creatorMatches
      condition: '/^dependabot/i'
```

## Explanations

Every condition produces a one-line explanation, such as `title does not match ^feat` or `3 changed line(s)`. The conventions feature uses these to say why a rule failed when the rule has no `message` of its own.
