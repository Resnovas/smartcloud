# Documentation writing standards

Documentation is a first-class deliverable. Apply these to KB articles, procedural guides, module docs, and any end-user facing how-to:

1. Detail level: someone with no prior experience must be able to follow every part. Define unavoidable jargon once.
2. Avoid UI chrome: do not describe page layout, button positions, icons, colours, or other visuals that may change.
3. Focus on actions: what to do and in what order, imperative verbs (Open, Select, Enter, Save, Confirm).
4. Facts only in body content: no marketing language ("best", "seamless"). Prefer costs, constraints, integration/compliance requirements, verifiable behaviour. If unknown: "unable to find relevant data".
5. Prefer the documentation-creator subagent for AsciiDoc/Guidance-style procedural and design docs.
6. Stay whitelabel in customer-facing docs (see whitelabel rule).

Project-specific taxonomy, import formats (e.g. Excel/HTML for a given KB), and workspace paths stay in that project's rules.
